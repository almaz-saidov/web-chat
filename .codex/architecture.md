# architecture.md

## Слои приложения

Основной поток зависимостей:

```text
route -> service -> repository -> model
```

### `api`

Слой HTTP/WebSocket входа.

Назначение:

- принять запрос или WebSocket-соединение;
- вызвать нужный сервис;
- вернуть HTTP-ответ или передать управление WebSocket-сервису.

В `api` не размещать бизнес-логику и SQL-запросы.

### `services`

Слой бизнес-логики.

Назначение:

- проверять сценарные условия;
- координировать работу репозиториев и вспомогательных сервисов;
- принимать решения уровня приложения.

Сервисы, работающие с БД, наследуются от `DatabaseService` и создают свой репозиторий через `_create_repository`.

### `database/repositories`

Слой доступа к данным.

Назначение:

- выполнять SQLAlchemy-запросы;
- работать с ORM-моделями;
- возвращать Pydantic-схемы наружу.

В репозиториях не размещать бизнес-логику.

### `database/models`

ORM-модели являются описанием таблиц БД.

### `schemas`

Pydantic-схемы описывают входные и выходные данные между слоями.

Схемы не должны содержать бизнес-логику, кроме валидации формы данных.

## Авторизация и токены

Архитектурная схема авторизации:

- access token — JWT, передается через `Authorization: Bearer <token>`;
- WebSocket получает access token через query-параметр `token`;
- refresh token хранится в http-only cookie и в таблице `refresh_tokens`;
- пароль хранится только как bcrypt-хэш.

`AuthService` является точкой координации авторизации: он использует `JWTService`, `CookiesService`, `UserService` и `RefreshTokenService`.

Текущее поведение refresh-токенов: при создании нового refresh-токена существующие токены пользователя удаляются. Фактически у пользователя один активный refresh-токен.

## Сообщения и WebSocket

Сохранение сообщения и рассылка разделены:

- сообщение сохраняется через HTTP endpoint `POST /api/message/create`;
- после сохранения клиент отправляет текст в WebSocket;
- WebSocket рассылает сообщение активным соединениям.

`ConnectionManager` хранит активные WebSocket-подключения в памяти процесса.

Архитектурные ограничения текущего решения:

- WebSocket-соединения не разделяются между несколькими процессами или контейнерами;
- WebSocket сам не сохраняет сообщения в БД;
- формат WebSocket-сообщения сейчас строковый, не JSON;
- время входящего WebSocket-сообщения клиент выставляет локально.

Для текущего размера проекта это допустимо. Внешний broker/pub-sub нужен только при задаче на масштабирование или несколько экземпляров приложения.

## Frontend

Frontend — статические HTML-страницы из `src/templates`, смонтированные на `/`.

Клиентская архитектура простая:

- без сборщика и frontend-фреймворка;
- access token хранится в `localStorage`;
- refresh token живет в cookie;
- HTTP-запросы выполняются через `fetch`;
- WebSocket подключается к `/api/ws?token=<access_token>`.

Не вводить frontend-сборку или отдельный SPA-фреймворк без отдельной архитектурной задачи.

## Границы изменений

При добавлении функциональности сохранять текущие границы:

- route только принимает запрос и вызывает service;
- service содержит сценарную логику;
- repository содержит SQL-запросы;
- model описывает таблицу;
- schema описывает данные на входе и выходе.
